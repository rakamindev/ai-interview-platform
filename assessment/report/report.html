In one paragraph. The Fit/Gap report is the only screen a hiring manager acts on, and on main it could not be trusted. The "Required" column was blank, assessor corrections were invisible, unprobed skills read like gaps, the report vanished or spun forever, and assessors could read other companies' candidates by id. The production build could not even boot. I rebuilt the slice end to end: a pure rule engine with explicit uncertainty, a report lifecycle with idempotent scheduling, tenant isolation, a model that is optional rather than blocking, a cross-service contract test, and a redesigned screen with a defined state for every situation.

Step 1 — Setup & local exploration

  • Cloned the repo and branched feat/trustworthy-fitgap off main. The work is split into small, reviewable commits, and the failing tests are committed before their fixes.
  • Ran Rails 7 / Ruby 3.3.2 (rbenv), PostgreSQL, Redis, Sidekiq and Vite locally, using fresh databases and an isolated Redis DB index so nothing else on the machine was touched. A Docker image was tried first and dropped because it built too slowly.
  • The interview needs Gemini Live, so I seeded fictional two-tenant data: an ended session, a complete portfolio and a vacancy including a skill that was never probed. I then exercised every fit/gap endpoint with curl and read the rows in Postgres and the Sidekiq logs.
  • Baseline: no specs, no web test runner, no CI. I added an RSpec harness (factories, tenant helpers, Sidekiq fake), Vitest + Testing Library, and GitHub Actions.
  • Two local-only quirks are documented in the README. On macOS, Puma's fork mode crashes, so local runs use single mode. CORS is limited to :5173.

Step 2 — Context & domain immersion

What the product does (observed, not inferred)

An assessor configures skills with L1–L5 behavioural anchors. A Gemini voice agent interviews the candidate while a coverage engine tracks which skills it has probed. Gemini Pro then writes a portfolio: a level, a confidence and evidence quotes per skill. The assessor can override any level. Finally, a Fit/Gap report compares the portfolio against a vacancy's expected levels and is exported to PDF. That report is the artefact that leaves the assessor's desk.

Industry: hiring in Indonesia

  • Volume vs. capacity: hundreds of applicants per opening and small HR teams. Screening calls are what gets rushed or skipped.
  • Commoditised: ATS, CV parsing, psychometric tests and video recording.
  • Leverage: a structured, evidence-backed judgement of skill at the cost of a screening call. Anchored structured interviews are among the most valid selection methods, and this product automates the structure.
  • Hard parts: code-switching between Bahasa Indonesia and English, mobile connectivity, inconsistent rubric use, and low trust in black-box AI scores.

What it is for, and what must stay true

Outcome: a hiring manager makes a faster and fairer next-step decision without re-interviewing. That holds only if (1) every number is right, since one visibly wrong row and assessors return to manual interviews; (2) uncertainty is honest, because missing evidence is not negative evidence; and (3) human corrections win and stay visible.

Step 3 — Problem & gap to the ideal condition

Core problem. The Fit/Gap report, the one artefact a hiring manager acts on, cannot be trusted. It shows blank required levels, hides human corrections, presents missing or thin evidence as gaps, can disappear or spin forever, and can be read across companies.
Ideal. Every row is correct, honest about certainty and provenance, always in a defined state, and visible only to its owner.

Constraint signal — what I would escalate to the Tech Lead

  1. Release blocker (F0): main cannot boot in production mode. Either production is not deployed from this tree, or it runs a config that is not in the repo. Confirm before any release.
  2. Tenancy is fail-open: TenantScoped falls back to all when no tenant resolves, and four tables carry no tenant_id. My per-endpoint fix is necessary but not sufficient. The long-term options (tenant_id everywhere, fail-closed scope, Postgres RLS) are a cross-team decision.
  3. Tenant is resolved from an unverified JWT decode; it is safe only because auth verifies afterwards on assessor routes.
  4. No retention or erasure path for transcripts and portfolios (UU PDP right to erasure). This needs a product and legal decision.
  5. Ambiguity: the brief's deadline (19 August) predates the working date. I assumed the portal deadline governs.

Self-derived acceptance criteria (33; full list in assessment/03-strategy.md)

Computation
  • Unprobed skill → not_assessed (reason not_probed), never a gap
  • Rating nil / 0 / 6 / "three" / 2.5 → not_assessed (invalid_rating), no exception
  • Override wins; AI level kept for audit; no verification flag
  • Low or unknown confidence → result computed but needs_verification
  • Labels match across case, whitespace, punctuation and diacritics
  • Vacancy with no skills → empty, complete report
Lifecycle & failure
  • First request → pending + exactly one job (202)
  • Repeated requests while in flight → no new job
  • Override → report kept, marked stale, one refresh queued
  • Model timeout / HTTP error / missing key / prose / {} → complete with flagged fallback
  • Unexpected error → failed + safe message; retries; never stuck
  • Writes atomic; overrides survive portfolio regeneration
Security & data
  • Other tenant's ids → 404, nothing queued or written
  • Worker refuses portfolio×vacancy from different tenants
  • 401 / 403 / 422 for missing token, wrong role, bad vacancy_id
  • Logs: ids only; PII parameters filtered
Presentation
  • Loading, generating, stale, failed, timeout, not-ready, not-available, error and empty states, each with a next action
  • Polling backs off, stops on terminal states, at ~2 min, and on unmount
  • Long labels clamp with full text available; long narrative collapses
  • No horizontal scroll at 390 px

AI verification moments

1. An assumed timestamp would have re-created the infinite spinner. Generated code used report.updated_at for the lost-job lease and wrote updated_at in the worker's failure path. fit_gap_reports has no timestamps. The worker spec showed the report stuck in generating because the rescue itself raised, which is exactly F5. Fix: an explicit queued_at lease column, plus a spec for the in-lease branch.

2. An "atomic" rewrite that was not atomic. The suggested transaction do … end joined the outer transaction. Even with a savepoint, the error handler's portfolio.update! autosaved the rolled-back skills back in. A partial-write spec kept returning duplicate rows; tracing sql.active_record showed ROLLBACK TO SAVEPOINT followed by an INSERT. Fix: requires_new: true and a reload before marking the portfolio failed.

Also: a factory for an association that does not exist (caught by reading the model), and a Tailwind class silently dropped by tailwind-merge (caught by inspecting computed style in the browser). Full log: assessment/04-ai-verification-log.md.

Protected data & rollout

  • Migration is additive with defaults, safe on existing rows and reversible. The worker signature is unchanged, so jobs queued during deploy still run. Legacy reports show as outdated and refresh on first view.
  • All portfolio, report, export and override endpoints are tenant-scoped (404); workers run as the owning tenant; vacancy_id is validated.
  • No secrets committed (application.yml and .env are git-ignored; CI uses dummy values). All names in specs, seeds and screenshots are fictional.

Assumptions & follow-ups

Assumptions
  • Tenant = organization (sessions.tenant_id); portfolios and reports inherit it.
  • The fit/gap report is the artefact hiring managers consume (PRD-02, Phase 5).
  • Low confidence (≤ 1 probe) should never be presented as final.
  • The portal deadline governs over the date printed in the brief.
