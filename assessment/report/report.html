Summary

The platform interviews a candidate with an AI voice, tracks which skills the conversation actually reached, rates each skill L1 to L5, compares the ratings with a vacancy and writes a recommendation that ends up in a PDF for the hiring manager.

The core problem: the product could not tell "we did not measure this" from "the candidate is weak at this". A skill the interview never reached was stored as L1, shown as "L1 Foundational", reported as a Gap and written into the hiring narrative as fact. A candidate whose audio dropped after one sentence received "Gap" on every skill and the line "not yet at the level to independently contribute". The assessor had no way to see it: the Required column was blank on every report, confidence was hidden, and correcting a rating broke the PDF export. Separately, any assessor could read and rescore another company's candidates by changing an id in the URL.

What shipped (one PR, both services)

  • Not assessed is a first-class state in the database, the API contract, the UI and the PDF; coverage gates every rating; model output is validated per skill; confidence follows the PRD rule.
  • Fit/gap tells the truth: required levels, provisional results, assessor overrides, stale and outdated reports, both narratives labelled as an AI draft.
  • Tenant isolation on every portfolio endpoint; no passwords or candidate data in logs.
  • One job at a time with visible retries and a way out of stalled runs; overrides are never destroyed; PDF export works for corrected portfolios and non-Latin names.
  • A test harness that did not exist: RSpec, Vitest, CI, and a contract file both suites check.

How the product was explored

The live audio interview is not reproducible on demand, so I seeded realistic transcripts and coverage maps for fake candidates in two tenants, then drove everything else through the real API, Sidekiq and Gemini: ending sessions, generating portfolios, overriding, fit/gap, export. Three scenarios carried most of the analysis:

  • Rina (fake): a strong 15-turn interview; one skill well probed, one partial, one asked once, one never discussed, one discovered.
  • Budi (fake): one answer, about a broken connection; every skill not_yet.
  • A second tenant with its own candidate, used only to test isolation.

Step 2: Context and domain immersion

The product, as it behaves

The code implies a careful pipeline: coverage states, a two-probe gate, a confidence rule in the PRD. In use, every one of those signals was dropped at the last step. The model was free to rate a skill the coverage map said was never reached, and the screens showed that rating with the same weight as a well-probed one.

The industry

For entry-level roles the scarce resource is a qualified person's time to talk to candidates. CV parsing, keyword screening, applicant tracking and online tests are commoditized. The leverage is a structured, evidence-backed signal about how a person thinks, produced at the cost of software, and it is only worth something if a recruiter trusts it enough not to re-interview. Candidates often join from a phone on a mobile connection, sometimes in a second language; dropped audio and mixed Bahasa Indonesia and English are normal conditions, not edge cases. (Qualitative reasoning; I did not find figures I could verify, so none are quoted.)

What has to stay true

  1. A rating must be earned. "Not assessed" is not "weak".
  2. Thin evidence must look thin. One question is a hint, three probes with quotes is a rating.
  3. A human stays in the loop, visibly. The override is the decision; AI text is a draft.
  4. Data stays with the company that collected it.

Step 3: Problem and gap analysis

Findings were reproduced on a running system with fake data, except the parts marked as read from code (the consent gap in F9, the production log level in N1). Two that did not hold up as written were downgraded (F4, F8); a report with a false finding is worse than a shorter one.

F1P0Defective implPortfolio, skill, override and fit/gap records are not tenant scoped. Impact: an assessor at company A downloaded, rescored (201) and ran fit/gap on company B's candidate.

F6P1Defect + missing specRetry during Sidekiq retries queues a second job; stalled runs cannot be restarted. Impact: duplicate model spend; a stuck result needs a developer.
F7P1DefectFit/gap page POSTs on every 404 while polling. Impact: two model calls per page view; the narrative changed under the reader.

Missing specification vs defective implementation

Never defined: what an unmeasured skill is called and how it counts; recovery from stuck generation; consent, retention, deletion and the candidate's right to contest; where culture-fit evidence comes from; how an override is audited. Defined but broken: tenant isolation, the PRD confidence rule, the fit/gap contract, atomic regeneration, one job per request, PDF export, log filtering, shipped model ids.

Constraint signal (escalated to a Tech Lead)

  1. Token contract with rakamin-api: does every token carry scheme? If not, N3 is a P0. Should this service verify tenant membership instead of trusting claims?
  2. Model ids and API version: the client hardcodes v1; current Pro models are not available there for new keys. Who owns model choice?
  3. UU PDP: lawful basis, consent text, retention, deletion, DPIA; whether AI recommendations need human review by policy.
  4. No tests, no CI before this change.
  5. Isolation by default scope relies on remembering a concern on every model; child tables have no tenant_id.

Step 4: Revamp strategy, acceptance criteria and trade-offs

Written before any product code changed (04-revamp-strategy.md, committed as dab60ca). The slice is the path from evidence to decision, because a wrong result there reaches a candidate; the P0 tenant fix and the cheap log fix come along because a "trustworthy report" another company can read would be hollow.

Acceptance criteria (condensed; each names its test layer in the source document)

ACCorrect behaviour, including the edge cases
AC1not_yet is Not assessed with no level or confidence, whatever the model says; zero candidate turns means no model call; never a gap; same in UI, PDF, JSON.
AC2Level 3, "3", "L3", 3.0 parse; nil, 0, 7, 2.5, "three", arrays become needs review, not L1. Evidence coerced to 3 strings of 500 chars; blank summary keeps the level; ids matched in any case; invented and duplicate skills dropped; non-JSON response retried with nothing written; a failure halfway leaves old rows intact.
AC3Confidence from coverage per PRD (high: covered and 3+ probes; medium: 2 probes or partial; low: 1 or initiated), weakest wins on overlap; the model's label is ignored.
AC4Every row shows required, candidate, confidence and result; low confidence is provisional; overrides flagged with the AI level; legacy reports served with defaults and marked stale; both narratives shown as a draft; empty vacancy has an empty state.
AC5Another tenant's ids return 404 on export (JSON, PDF), fit/gap read, generate and regenerate, and override; workers still find records.
AC6Regeneration updates skills in place and keeps overrides, even when a skill becomes not assessed; an override of an unassessed skill needs a note; notes capped at 2,000.
AC7One fit/gap job per pair across tabs; the page POSTs once; between retries the portfolio stays generating with the reason and Retry is refused (409).
AC8A run stuck for 20 minutes is reported as stalled and can be restarted.
AC9PDF export works with an override, Indonesian, Greek, Cyrillic, CJK, emoji and 5,000-char text; failures are shown in the UI.
AC10Passwords, tokens, emails, candidate names, notes and transcript text are filtered from logs.
AC11Loading, empty, not assessed, needs review, low confidence, partial, generating, stalled, failed, fetch error, long text, 375 px without horizontal scroll.

AI verification moments (9 real entries in ai-verification-log.md)

The error path saved a half-written skill. My first generator built new skills through the association. When a save failed inside the transaction, the existing rescue called portfolio.update!, which autosaved the unsaved skill outside the rolled-back transaction: exactly the partial write this change was meant to remove, and it would have happened in production. The atomicity spec caught it; I found the cause by printing the surviving rows instead of guessing.

A wrong explanation, corrected. I first blamed nested transactions and logged a symptom I had not observed. Re-reading the log, I tested the claim (removed requires_new; every spec still passed: RSpec's transaction is non-joinable) and corrected the entry and the code comment in a separate commit.

Also logged: a shell quirk that made every model look like a 404; trusting a metadata endpoint; a regenerate path that made every just-queued run look stalled (caught reviewing my diff, spec first); two wrong test expectations fixed by making one stricter, not looser; a "missing name" that was a screenshot taken mid-load; a fake test password a secret scanner flagged on the PR; and a lock any job could release, found while listing failure modes and fixed with a token-owned lock.

Limits, follow-ups and assumptions

Stated limits

  • The live audio interview was not run; transcripts and coverage maps were seeded. Everything after the interview used the real API, workers and model.
  • Local runs used gemini-2.5-flash for both model roles; production model choice is open (N2).
  • CI is configured but has not run on GitHub before this submission.
  • The model still writes a hiring recommendation. It is now labelled a draft and no longer built on unmeasured skills; whether the product should write one at all is a product and legal decision (Pasal 10), escalated rather than decided here.

Follow-ups, in priority order

  1. Consent notice, retention period and deletion path for audio, transcripts and portfolios; a candidate-facing way to object (F9).
  2. Confirm the token contract with rakamin-api; reject tenant selection by header for authenticated requests if possible (N3).
  3. tenant_id on child tables as a second isolation layer.
  4. Settle production model ids and API version; add JSON-schema output on top of the normalizer.
  5. Backfill task for portfolios generated before this change; evidence grounding (quotes must appear in the transcript).

Assumptions (no live Q&A)

  1. not_yet means no evidence was collected, whatever the model says.
  2. initiated with one probe is a real but thin signal: rated, low confidence, provisional in fit/gap.
  3. Where the PRD confidence rules overlap, the weaker label wins.
  4. An assessor override is the effective level for every downstream use.
  5. "Required" in the UI is the vacancy skill's expected_level.
  6. Narratives are drafts for the assessor, not statements to send unreviewed.
  7. The submission deadline is the one shown on the career dashboard, which differs from the brief.
