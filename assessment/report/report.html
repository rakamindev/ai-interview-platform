1. Summary

The core problem. When an interview ends before every skill is discussed (time limit, connection error, candidate leaves), the platform still gives each undiscussed skill a level. Any missing or invalid model level is silently coerced to L1 by .to_i.clamp(1, 5). The fit/gap report then shows that fabricated L1 as "Gap −2", the AI writes a hiring recommendation from it, and the screen presents it with the same authority as a well-evidenced rating.

A candidate who was never asked about a skill is reported as weak at it. They did not choose this tool and cannot see or contest the result.

What I changed. Whether a skill was assessed is now decided from data the system already has (the coverage map), not guessed by the model. Each skill is assessed, insufficient_evidence, or not_assessed. Only assessed skills carry a level, and confidence is computed rather than self-reported. That one rule flows through storage, fit/gap, the narrative prompt, the PDF export, and the UI.

Along the way I found and fixed a cross-tenant data leak (P0), verified against the running API, plus a broken API/UI field contract that left the "Required" column blank in every report.

3. Product context

What the product is for

It replaces a first-round human technical interview with an AI voice interviewer that probes skills, then produces an evidence-backed L1–L5 portfolio that a recruiter compares against a vacancy. The outcome it exists to produce is a trustworthy hiring signal at scale. Everything rests on that signal being trustworthy: if recruiters learn that a level can be invented, they stop relying on any level, and the product loses its reason to exist.

The industry

In Indonesian tech hiring, the scarce resource is senior interviewer time, not candidate volume. Screening tools such as CV parsing and generic aptitude tests are commoditised. The leverage is in depth: evidence of how someone thinks, at a level a hiring manager will act on. That only works if the system is honest about where its evidence stops.

UU PDP implications (Law No. 27 of 2022 on Personal Data Protection)

  • Accuracy. Storing and sharing an invented assessment about a person conflicts with the controller's duty to keep personal data accurate. The fix stores "unknown" instead of a false value.
  • Confidentiality and access control. The cross-tenant leak exposed candidate transcripts, quotes, and ratings to other organisations. Fixed in this PR.
  • Automated decision-making. The law gives data subjects rights regarding decisions based solely on automated processing, including profiling. Keeping a human override, making it visible, and never presenting missing evidence as a judgement all reduce that risk. Whether this product needs an explicit objection channel for candidates is a legal question I'm escalating (constraint signal 2).
  • Lawful basis and transparency. Candidates are told "The interview has been recorded" only after the session. This is Pending legal/product decision; I did not change the consent flow because the lawful basis is not an engineering call.
  • Logs. Error messages could carry raw model output, which can include candidate quotes, into logs, the database, and API responses. These are now generic.

Constraint signals (what I would escalate to a Tech Lead)

  1. Tenant isolation is a live breach. I'd ship that commit on its own first, ahead of the larger revamp, and audit access logs for cross-tenant portfolio IDs.
  2. Consent, retention, and automated-decision rights need a legal/product owner. Engineering can only make the gap visible.
  3. Shared database. The README says rakamin-api shares this PostgreSQL. Making portfolio_skills.ai_level nullable needs confirmation that no other consumer assumes NOT NULL.
  4. Historical reports computed with the old logic still contain fabricated gaps. Re-generating them is an ops decision, and so is whether to tell affected tenants.
  5. Production boot. RAILS_ENV=production rails runner fails locally with undefined method 'active_job', and eager loading fails on a Zeitwerk name mismatch (audio_websocket_middleware.rb vs AudioWebSocketMiddleware). Both predate this work and were left untouched to keep scope tight. CI therefore runs without eager loading.
  6. Auth trusts JWT claims without a user lookup, with a 3-day TTL in the sample config. A revoked assessor keeps access for days.

Smaller decisions and rejected options.

  • string + CHECK constraint instead of a PG enum for the status, because enum values can't be removed cleanly in a rollback.
  • No unique index on (portfolio_id, skill_label) yet. Existing rows may hold duplicates, so the deploy could fail. Duplicates are prevented at the job level instead.
  • Overrides are disallowed on unrated skills. Inventing a level without evidence recreates the bug; the UI suggests a follow-up session instead.
  • A Redis SET NX lock for fit/gap enqueue plus an upsert in the engine. Either alone leaves a gap: the lock prevents wasted LLM calls, and the upsert makes a duplicate harmless.

7. What shipped

Backend (api/)

  • Migration 20261019000000: adds assessment_status (default assessed, so existing rows stay valid), makes level, confidence, and summary nullable, and replaces the level CHECK with a NULL-safe status/level constraint. The down refuses while unrated rows exist. 20261019000001 adds generation_started_at for stale-claim recovery.
  • Portfolios::Generator: builds rows from coverage maps; only discussed skills are rated by the model; atomic claim (update_all on pending|failed|stale generating); one transaction; safe error messages; the model client is built lazily (not needed when nothing was discussed).
  • Portfolios::ResponseParser validates the model JSON. Portfolios::Confidence encodes the PRD rule.
  • FitGap::Engine: not_assessed with a reason, is_override, upsert, a narrative prompt that forbids treating unknowns as weakness, and an honest fallback.
  • Tenant scoping via for_current_tenant scopes that go through the tenant-scoped Session.
  • FitGapGeneratorWorker.enqueue_once (Redis SET NX EX, released in ensure). Override guard. PDF export prints unrated skills as such.
  • rails demo:seed: synthetic early-ended interview through the real generator with a stubbed model.

Frontend (web/)

  • Types now match the API contract (expected_level, nullable level, assessment_status, is_override, not_assessed_reason). parseLevel and its fallback to 1 are removed.
  • Unrated skill card: a dashed "No rating" slot in place of a level, an explanation of why, and the next step. No override button.
  • Portfolio summary: "2 of 5 configured skills rated" with a segmented bar and why the interview ended early.
  • Fit/gap: the Required column fixed, reason under each unrated row, override marker, not-assessed count, a warning banner, the overall assessment shown, and a stacked layout on mobile.
  • Explicit page states (loading, generating, failed with retry, load error, not ready, timed out). Long text wraps or collapses. The header fits at 375 px.
  • Everything built from the existing tokens and Radix/shadcn primitives; no new visual language.

AI verification moments

I used an AI coding assistant throughout. These are the cases where its output was wrong or risky, and how I caught them.

  1. A CHECK constraint that let NULL through. The generated constraint was (status = 'assessed' AND ai_level BETWEEN 1 AND 5) OR (status <> 'assessed' AND ai_level IS NULL). It reads correctly, but in SQL's three-valued logic an assessed row with a NULL level evaluates to NULL OR FALSE = NULL, and PostgreSQL treats a NULL CHECK as passing. I caught it by inserting that exact row with raw SQL: it was accepted. Fixed with ai_level IS NOT NULL, re-verified (now PG::CheckViolation), and pinned with a model spec that bypasses validations. Evidence: evidence/03a-… (bug) and 03-… (fixed).
  2. Status stuck in "generating". The generated atomic claim used update_all, which bypasses the in-memory object. On failure, portfolio.update!(generation_status: 'failed') saw no change from the stale in-memory value and wrote nothing, so the portfolio would spin forever. The "save fails half-way" spec caught it (expected "failed", got "generating"). Fixed by reloading after a successful claim.
  3. A wrong assumption about Rails scopes. The assistant's plan avoided joins(:session) on the belief that it ignores Session's tenant default_scope. Checking the generated SQL showed it does apply it. I kept the explicit subquery anyway because it doesn't depend on that subtle behaviour, but the stated reason was wrong.
  4. Invalid evidence, caught before it was used. The first migration-safety log "proved" rollback worked, but the probe row had silently failed to insert because model validations weren't updated yet, so the rollback ran against nothing. I re-ran the check with raw SQL inserts.

10. Known limitations and follow-ups

  • The live voice interview was not exercised (no Gemini key). The generator change is covered by specs and the stubbed demo, not by a real model run.
  • audio_complete hardening (P0-3): verify coverage or session state server-side. Not done, because its timing with the WebSocket flow can't be tested here.
  • regenerate_fitgap should keep the old report until the new one succeeds (P2-6).
  • Unique index on (portfolio_id, skill_label) after a duplicate audit.
  • Candidate notice and consent before recording, and a retention policy: legal decision first.
  • Re-generate historical fit/gap reports affected by fabricated L1s.
  • Production boot and eager-load issues (constraint signal 5).
