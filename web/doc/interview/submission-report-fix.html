Bagian 1

Asumsi Global

Sebelum masuk ke analisa, saya tetapkan beberapa asumsi kerja agar pengerjaan tetap fokus. Kalau ada yang tidak pas dengan konteks bisnis Rakamin, semuanya mudah disesuaikan.

  • Stack tidak diganti. Rails + React + PostgreSQL + Sidekiq + Gemini API adalah fondasi yang dipakai. Saya tidak mempermasalahkan pemilihan stack, fokus ke pengerjaan di atas fondasi yang ada.
  • Multi-tenant berbasis isolasi baris (row-level). Isolasi data antar tenant dilakukan lewat kolom tenant_id di tiap tabel.
  • Isolasi data antar tenant di database. Data tenant dan data bersama (seperti organizations) diperlakukan terpisah, mengikuti struktur yang sudah ada.
  • Sidekiq + Redis untuk background jobs. Coverage analysis, portfolio generation, dan fit-gap semuanya async via Sidekiq. Ini diasumsikan selalu berjalan saat demo.
  • Gemini API bisa berubah. Model yang tersedia di Gemini bisa deprecated tanpa pemberitahuan — sehingga konfigurasi model tidak boleh di-hardcode, harus lewat environment config.
  • Kandidat tidak punya akun. Akses interview dilakukan via invite_token di URL — bukan sistem register/login terpisah. Ini desain yang disengaja, bukan bolong.
  • Demo environment = localhost. Subdomain tenant (misal ai-interview.localhost) dipetakan ke 127.0.0.1 lewat edit /etc/hosts manual.
Bagian 2

Konteks Produk & Domain

Apa yang Dibangun

AI Interview Platform adalah alat wawancara kandidat berbasis suara real-time yang ditenagai Gemini Live API. Platform ini bukan chatbot biasa — AI berperan sebagai pewawancara yang aktif menilai cakupan skill (coverage) kandidat terhadap rubrik assessment yang sudah ditentukan, lalu menghasilkan portfolio penilaian yang bisa dibandingkan dengan lowongan yang ada (fit-gap report).

Alur utamanya sederhana tapi teknis cukup dalam:

Admin buat assessment (rubrik skill + role title) ↓ Invite kandidat via link token ↓ Kandidat interview suara real-time dengan AI ↓ (async, background) Coverage analyzer menilai tiap skill dari percakapan ↓ Portfolio kandidat di-generate otomatis ↓ Admin bisa bandingkan portfolio vs vacancy (fit-gap report)

Siapa Penggunanya

Pengguna Internal

Pengguna internal yang bikin assessment, invite kandidat, pantau progres interview live, dan review hasil portfolio. Mereka login dengan akun yang terikat ke tenant masing-masing.

Kandidat

Tidak punya akun — masuk via link invite yang berisi token. Mereka tidak memilih platform ini dan tidak bisa opt-out. Pengalaman mereka sangat menentukan kualitas penilaian.

Konteks Industri: Hiring di Indonesia

Interview teknis di Indonesia masih banyak bergantung pada kemampuan manusia pewawancara yang bisa berbeda-beda standarnya. AI Interview Platform mencoba menstandarkan proses penilaian — AI menilai coverage berdasarkan rubrik yang sama untuk semua kandidat, mengurangi bias evaluasi. Ini relevan dengan UU PDP (Perlindungan Data Pribadi) Indonesia: percakapan kandidat, transcript, dan hasil penilaian adalah data pribadi yang sensitif — tidak boleh ada di log, tidak boleh bocor ke tenant lain.

Implikasi UU PDP: Data kandidat (nama, transcript percakapan, hasil penilaian) harus terisolasi per tenant, tidak boleh keluar lewat log server, dan penggunaan API key pihak ketiga (Gemini) perlu diperhatikan karena data kandidat dikirim ke server Google untuk diproses.
Bagian 3

Analisa Gap & Temuan (P0–P3)

Sebelum menulis satu baris kode, saya baca seluruh codebase: routing config, controller, model, frontend pages, dan mencoba interview end-to-end. Hasilnya saya kategorikan berdasarkan dampak ke kelayakan demo dan kualitas produk.

Definisi prioritas: P0 = blocker demo tidak bisa jalan | P1 = fitur inti yang dievaluasi | P2 = kualitas dan kejelasan produk | P3 = polesan dan dokumentasi

Temuan Kritis (P0 — Demo Tidak Bisa Jalan)

P0

Model Gemini yang di-hardcode sudah deprecated

Kode memakai gemini-2.0-flash-001 dan gemini-2.0-pro-001 yang di-hardcode langsung di source — model ini sudah tidak tersedia di Gemini API dan mengembalikan 401/404. Artinya seluruh fitur utama (interview live, coverage analysis, portfolio generation) tidak bisa jalan sama sekali tanpa fix ini.

P0

Kandidat tidak bisa masuk sesi interview

Alur hardware check dan invite link bermasalah — kandidat gagal lolos pemeriksaan perangkat sebelum interview dimulai. Ini blocker langsung untuk alur utama yang menjadi inti penilaian.

Temuan Inti Interview (P1 — Kualitas Fitur Utama)

P1

AI memotong kandidat saat jeda bicara

VAD (Voice Activity Detection) Gemini terlalu agresif dengan silence pump delay 1 detik — jeda berpikir kandidat dianggap selesai bicara, sehingga AI langsung nyela. Ini merusak kenyamanan wawancara secara fundamental.

P1

Teks sinyal internal bocor diucapkan AI

System prompt yang terlalu panjang dan detail soal sinyal tersembunyi justru memancing model untuk mengucapkan teks internal itu. Terbukti dari transcript sesi 2: AI mengucapkan "Wait, input contains valid wrap_up signal..." — padahal itu pesan internal yang tidak boleh didengar kandidat.

P1

Sesi interview berakhir dini tanpa verifikasi backend

AI menutup interview sendiri di turn ke-17 dengan reason all_covered — padahal 2 skill masih belum tercakup dan masih ada jatah 45 menit. Backend langsung percaya pada kata AI tanpa verifikasi coverage yang sesungguhnya. Ini adalah bug arsitektur: keputusan mengakhiri interview seharusnya sepenuhnya milik backend.

P1

Login tidak pakai database — backdoor token via env

Tabel users kosong; akses admin dilakukan via VITE_DEV_TOKEN yang di-inject langsung dari environment variable ke frontend. Ini backdoor yang tidak boleh ada di sistem produksi — siapapun yang tahu token bisa masuk tanpa kredensial.

Temuan Kualitas Produk (P2 — Penyempurnaan)

P2

Pesan error login tidak jujur / tidak membantu

Error login hanya mengembalikan pesan generik — tidak membedakan antara email tidak ditemukan, password salah, atau akun tidak punya akses ke tenant ini. Assessor tidak tahu harus apa.

P2

Role assessor ada di kode tapi belum real

Di AuthorizeApiRequest, ada komentar jujur: "assessor is planned as a future role." Semua fitur sekarang eksklusif untuk admin. Ini temuan arsitektur yang perlu diangkat — role system sudah disiapkan tapi belum diimplementasi.

P2

SignupPage.tsx — halaman yatim piatu

File ada (106 baris, sudah jadi), tapi tidak pernah di-routing di App.tsx, dan backend tidak punya endpoint register sama sekali. Ini dead code yang perlu dibersihkan agar tidak membingungkan.

P2

Frontend reconnect menyerah terlalu cepat vs grace period backend

Frontend hanya mencoba reconnect 3× (7 detik total) lalu menampilkan "Interview Complete" — menyesatkan, karena sesi belum selesai. Backend masih punya grace period 120 detik. Ini mismatch yang merugikan kandidat dengan koneksi tidak stabil.

Bagian 4

Strategi Revamp & Trade-off

Prinsip Pengerjaan

Saya pakai prinsip KISS (Keep It Simple) secara konsisten: selesaikan yang paling penting untuk demo lebih dulu, hindari over-engineering, jangan tambah fitur sebelum inti stabil. Urutan pengerjaan mengikuti prioritas P0 → P1 → P2 → P3, bukan semuanya sekaligus.

Trade-off Utama yang Diputuskan

1. Multi-tenant: resolusi tenant lewat subdomain

Tenant ditentukan dari request.host di backend — ai-interview.localhost → tenant AI Interview Test, acme.localhost → tenant Acme Corp. Tidak ada input dari client yang dipercaya untuk menentukan tenant. Subdomain adalah carrier identitas tenant yang natural (sama seperti Slack dan Notion: acme.slack.com). Login di subdomain tidak dikenal mengembalikan 401 "Tenant not recognized", bukan fallback diam-diam ke tenant lain.

2. User-Tenant: Kolom Tunggal vs Membership Table

Opsi A — Kolom tenant_id di tabel users (yang dipilih)

Satu user = satu tenant. Sederhana, cukup untuk isolasi demo, dan tidak membutuhkan migrasi besar.

Opsi B — Membership table user↔tenant (many-to-many)

User bisa punya akses ke beberapa tenant. Lebih fleksibel untuk production, tapi over-engineering untuk scope demo ini.

Alasan memilih A: YAGNI (You Aren't Gonna Need It) — untuk membuktikan isolasi tenant dalam demo, satu user satu tenant sudah cukup. Membership table bisa ditambahkan nanti tanpa merusak fondasi yang ada.

3. System Prompt: Tetap Detail vs Dipangkas

Opsi A — Dipangkas, instruksi singkat & imperatif (yang dipilih)

Rule dibuat ringkas dan tegas. "YOU CANNOT CLOSE THE INTERVIEW — Only the system can end it." Bukan kuliah panjang soal bagaimana sinyal bekerja.

Opsi B — Tetap detail, tambah lebih banyak larangan

Menambah lebih banyak instruksi tentang apa yang tidak boleh dilakukan AI. Secara teori lebih komprehensif.

Alasan memilih A: Instruksi panjang yang menjelaskan detail tentang sinyal tersembunyi justru memancing model untuk mengucapkannya — ini "prompt injection oleh diri sendiri." Instruksi singkat dan imperatif lebih efektif. Terbukti dari perbandingan transcript sebelum dan sesudah fix.

Constraint Signal yang saya angkat: Kebocoran cross-tenant via Portfolio.find(id) yang tidak di-scope (unscoped find) belum saya perbaiki dalam pengerjaan ini — ini debt arsitektur yang harus diselesaikan sebelum production deployment. Tercatat di backlog.
Bagian 5

Implementasi — Apa yang Dikerjakan

Pengerjaan dibagi dalam 4 phase berurutan. Tiap phase selesai → saya test di browser → konfirmasi → lanjut. Tidak ada yang langsung ditulis sekaligus.

Phase 0 — Fondasi & Blocker

Konfigurasi model Gemini via environment

Model tidak lagi di-hardcode. Sekarang baca dari application.yml: GEMINI_LIVE_MODEL untuk interview suara, GEMINI_FLASH_MODEL untuk coverage analysis, GEMINI_PRO_MODEL untuk portfolio generation. Satu titik konfigurasi, mudah diganti tanpa ubah kode.

Perbaikan alur kandidat masuk sesi

Fix hardware check dan invite link — kandidat bisa lolos pemeriksaan perangkat dan masuk ke sesi interview. Tanpa ini seluruh demo tidak bisa berjalan.

Phase 1 — Inti Interview

Silence pump delay: 1s → 2.5s

Di live_client.rb, SILENCE_PUMP_DELAY dinaikkan dari 1 detik ke 2.5 detik. Ini memberi ruang berpikir bagi kandidat sebelum AI merespons. 2.5 detik adalah kompromi setelah observasi langsung — cukup untuk berpikir, tidak terlalu lama sampai wawancara terasa lambat.

System prompt dipangkas & instruksi dipertegas

Prompt turun dari ±10KB ke ±8.6KB. Rule 7 diubah jadi tegas: AI tidak bisa menutup interview — hanya sistem yang bisa. Rule 9 untuk wrap-up dibuat singkat: maksimal 2 kalimat, hanya kalau sistem memberi sinyal. Prompt di-cache di DB, jadi perlu di-regenerate via rails runner agar langsung efektif.

End-sesi hanya via backend, bukan via kata AI

Logika closing-phrase fallback diubah: backend hanya memfinalisasi sesi kalau coverage_pending sudah benar (semua skill verified covered). Kalau AI menutup lebih awal, backend kirim CONTINUE_SIGNAL untuk menyuruh lanjut — dibatasi maksimal 3×. Ini prinsip penting: model tidak dipercaya untuk keputusan bisnis seperti mengakhiri interview.

Graceful exit — AI tutup dengan sopan & transparan

Sebelumnya AI langsung bilang "Terima kasih atas waktunya" tanpa menjelaskan kenapa interview berakhir — kandidat merasa di-ghosting. Sekarang: AI jawab pertanyaan kandidat dulu, jelaskan bahwa semua topik sudah tercakup, baru tutup secara natural. Efisiensi dipertahankan — interview boleh selesai cepat kalau skill sudah covered, yang diperbaiki cara keluarnya.

Login sungguhan via database

Seed akun demo untuk login, pesan error dibedakan (email tidak ditemukan / password salah / akun tidak punya akses), backdoor VITE_DEV_TOKEN dihapus dari kode FE dan file env. Tabel users yang tadinya kosong sekarang terisi dengan akun yang bisa dipakai demo.

Phase 4 — Bug Fixes & Resilience

Auto-end saat kandidat pamitan

Kandidat pamitan (ucapan terima kasih di akhir) harus selalu dihormati, apapun status coverage. Branch C fallback inject WRAP_UP_SIGNAL langsung tanpa menunggu coverage_pending. Backend boleh override keputusan AI (untuk cegah premature end), tapi tidak boleh override keputusan kandidat.

Fix loop nudge kontradiktif menjelang waktu habis

Ditambah check time_critical — kalau warning waktu sudah terkirim, AI closing langsung difinalisasi, bukan di-nudge untuk lanjut. Dua sinyal berlawanan (coverage map bilang "wrap up", nudge bilang "lanjut") diputuskan tegas: sinyal waktu adalah source of truth tertinggi.

Reconnect frontend diselaraskan dengan grace period backend

RECONNECT_DELAYS diperpanjang dari 3 attempts (7 detik) ke 8 attempts (~247 detik) — sinkron dengan grace period backend 120 detik. Ditambah state "failed" dengan tombol "Retry Interview" yang jelas, bukan langsung tampil "Interview Complete" yang menyesatkan.

Self-hosted speed test endpoint

Speed test memakai endpoint /api/v1/speed-test di backend sendiri sebagai primary, dengan httpbin sebagai fallback. Alasan memilih self-hosted: httpbin.org sering return 503 atau timeout dan tidak selalu tersedia, sehingga tidak bisa diandalkan. Endpoint sendiri bebas dari masalah itu — dan ketika aplikasi benar-benar di-hosting di server, pengukuran ke endpoint ini akan mencerminkan koneksi ke server secara akurat. Batasannya saat ini: karena demo masih berjalan di localhost, pengukuran ke endpoint self-hosted belum sepenuhnya merepresentasikan kecepatan internet kandidat — ini keterbatasan lingkungan demo, bukan desain solusinya.

Time warning 10 menit

Sebelumnya warning baru muncul di 2 menit dan 1 menit — terlalu mendadak. Ditambah tier :warn_600 di backend (10 menit sebelum habis) dan banner amber di frontend yang auto-dismiss setelah 5 detik. Kandidat yang tahu waktu tersisa bisa mengatur panjang jawaban.

Multi-Tenant (Subdomain-Based)

Ini satu modul tersendiri yang cukup dalam. Kondisi sebelumnya: login bisa "pilih tenant seenaknya" via header X-Tenant-Scheme — client bisa kirim header apapun dan backend percaya. Sesudah implementasi:

  • Kolom tenant_id ditambahkan ke tabel users via migration yang aman (nullable, tanpa FK)
  • Method Organization.find_by_host baru — strict match tanpa fallback ke org default
  • Login validate: subdomain → cari org → cek user.tenant_id == org.id → baru mint JWT
  • Frontend derive host dari window.location.hostname, bukan hardcode
  • Tenant name muncul di header dari DB hasil login, bukan dari env
  • Seeds: 3 tenant + user terikat per tenant, idempotent via find_or_initialize_by
Hasil: Login di acme.localhost dengan akun rakamin → 401 "Account is not authorized for this tenant." Login di subdomain tidak dikenal → 401 "Tenant not recognized."

Bagian 8

Backlog & Catatan Jujur

Ini hal-hal yang saya tahu belum selesai atau perlu diperhatikan. Saya tulis jujur karena lebih berguna daripada berpura-pura semuanya beres.

ItemKeteranganPrioritas
Cross-tenant data leak via unscoped find Portfolio.find(id) tidak di-scope ke tenant — assessor dari tenant lain bisa akses portfolio kalau tahu ID. Ini security debt yang harus diselesaikan sebelum production. P1
Denormalisasi tenant_id ke child tables Portfolio, PortfolioSkill, FitGapReport, dan tabel turunan lainnya tidak punya tenant_id langsung — isolasi bergantung pada parent FK. Butuh migrasi + backfill besar kalau mau di-enforce di level DB. P3
Role assessor belum real Role ada di permission list tapi implementasinya masih sama dengan admin. Kalau mau ada tim assessor terpisah, butuh scoping data per-assessor. P2
