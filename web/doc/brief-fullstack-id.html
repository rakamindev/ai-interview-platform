03

Definisikan Masalah & Gap ke Kondisi Ideal

Jelajahi workflow nyata dari ujung ke ujung, inspeksi record database, dan evaluasi API payload untuk mengidentifikasi gap antara implementasi yang cacat saat ini dan kondisi produk yang ideal.

Selesai ketika:

  • Kamu mengartikulasikan masalah inti dan gap yang mencegah produk ini memberikan nilai nyata kepada pengguna dan kandidat.
  • Temuan dikategorikan berdasarkan keparahan (P0–P3) dengan pernyataan dampak satu baris.
  • Kamu memisahkan spesifikasi yang hilang (belum pernah didefinisikan) dari implementasi yang cacat (didefinisikan tapi rusak).
  • Temuan mencakup kedua service (api/ dan web/), termasuk seam komputasi data dan presentasi frontend.
  • Constraint Signal: Kamu mengidentifikasi dan mendokumentasikan risiko pemblokiran atau debt arsitektur yang akan kamu eskalasi ke Tech Lead di proyek nyata.
Kategori Keparahan:
P0 · Kritis

Pemblokir

Merusak fungsionalitas inti atau menyebabkan kerusakan data. Harus diperbaiki segera.

P1 · Tinggi

Berdampak Signifikan

Secara serius merusak workflow pengguna atau akurasi penilaian kandidat.

P2 · Sedang

Pengalaman Buruk

Mengurangi kualitas produk tapi ada workaround. Perlu ditangani segera.

P3 · Rendah

Enhancement

Perbaikan kecil atau optimisasi yang meningkatkan kualitas tapi bukan blocker.

04

Strategi Revamp, Acceptance Criteria & Trade-offs

Rancang revamp yang secara langsung menjembatani gap ke kondisi produk ideal, mencakup modul backend dan frontend.

  1. Turunkan Acceptance Criteria Sendiri: Tuliskan apa arti perilaku yang benar untuk setiap input dan edge case (skill yang belum dinilai, rating yang hilang, kegagalan model call, tipe data edge-case, dan state teks panjang).
  2. Evaluasi Opsi Solusi & Trade-offs: Bandingkan setidaknya dua atau tiga opsi teknis untuk meng-ship revamp ini:

    Opsi A

    Jelaskan opsi teknis pertama — apa yang dibeli, apa biayanya, dan apa yang ditutup oleh opsi ini.

    Opsi B

    Jelaskan opsi teknis alternatif — dampak produk vs cost, maintainability jangka panjang, dan failure modes.

Yang dievaluasi per opsi: Dampak Produk vs Cost · Maintainability Jangka Panjang · Failure Modes · Contextual Fit
05

Implementasi Monozukuri & Pull Request

Land perubahanmu di seluruh stack: API, data model di bawahnya, screen frontend, dan automated tests.

Standar Baseline Minimum:
  • Proven Correctness: Test gagal jika behavior regresi, dan kamu telah menyaksikannya gagal.
  • Designed Failure Paths: Tangani timeout, partial write, model error, dan duplicate job secara eksplisit.
  • Protected Data: Migrasi harus reversible dan aman terhadap baris yang ada. Endpoint terautorisasi, input tervalidasi, tidak ada data personal sensitif di log atau commit (kepatuhan UU PDP).
  • Polished UI/UX: Tampilan visual yang bagus, layout yang harmonis, semua interaction state (loading, empty, error, partial, teks panjang, responsive).
  • Seeded Fault Test: Buktikan test kamu nyata dengan mematahkan logika di scratch branch untuk menunjukkan test menangkapnya, lalu revert.
  • AI Verification Moment: Dokumentasikan setidaknya satu instance di mana AI code generation salah atau berisiko dan bagaimana kamu memverifikasi/memperbaikinya.
Opsi Struktur Pull Request:

PR Tunggal

Satu Pull Request komprehensif yang berisi perubahan penuh di kedua service.

Umbrella PR

PR umbrella yang menetapkan visi keseluruhan dan ditautkan ke beberapa sub-PR yang terfokus.
