Assessor Decision Integrity

Tenant-safe overrides, an append-only audit trail, and fit/gap reports you can defend

Case Study: Fullstack Product Engineer Repository: rakamindev/ai-interview-platform Pull request: #242 Candidate: Muhammad Nazih

1. Summary

The fit/gap report is the document a recruiter exports to justify a hiring decision. Today that document cannot be defended: portfolio reads are not scoped to the requesting organization, and an assessor can silently change a skill rating with no record of who did it or why. I hardened that decision path across both services — tenant-safe portfolio access, a mandatory override rationale with an append-only history, and fit/gap regeneration that never destroys the last good report.

The work is backend-heavy (data model, authorization, audit, background-job correctness) with a focused frontend slice: an override dialog, visible provenance, and honest loading / empty / pending / failed states. Every behavior is covered by request specs, and the seeded-fault evidence in §7 shows the tests failing when the fix is removed.

2. Product context

Who uses it

  • Assessors — review transcript evidence and skill ratings, then decide whether a candidate fits a vacancy.
  • Recruiters and hiring managers — export the fit/gap report and act on it.
  • Candidates — the people being measured. They do not choose this product, cannot opt out, and a wrong rating changes a real person's year.

What must stay true

  • One organization's data is never visible to another organization.
  • Every human correction of an AI rating is attributable, reasoned, and permanent.
  • The exported report reflects the latest decision state, and a failed background job never makes it unavailable.

UU PDP implications

Candidate transcripts, skill evidence, and ratings are personal data. This change keeps them inside the tenant that created them, adds an immutable record of human edits, logs no personal content, and uses fictional seed data for demonstration. No real candidate data is committed.

Missing specification vs. defect. PRD 02 Phase 5 defines the review flow as: read evidence, accept the AI rating, run fit/gap, export. 4. Option evaluation

Two decisions drove the design. Each was evaluated against cost, benefit, maintenance, failure modes, and fit for this codebase.

DecisionOption AOption BOption CChosen
Tenant scoping Add portfolios.tenant_id + existing TenantScoped Join-only predicate at each call site Postgres row-level security A — consistent with assessments/sessions, safe by default, no infra change
Audit storage Separate append-only table Overwrite assessor_overrides with history columns Generic event-sourcing log A — decision record must be reconstructable; current value stays fast to read
Report freshness Version counter gated on override Delete cached report on override Timestamp comparison A — timestamps are unreliable; version is explicit and testable

5. Solution design

Data model

portfolios
  + tenant_id                bigint  not null  (backfilled from sessions.tenant_id)
  + overrides_version        integer not null default 0

fit_gap_reports
  + computed_overrides_version integer not null default 0

assessor_override_versions   -- new, append-only
  portfolio_skill_id, tenant_id, version, ai_level, override_level,
  reason, actor_id, actor_role, created_at
  unique (portfolio_skill_id, version)

API contract

POST /api/v1/portfolio_skills/:id/override
  201 { override: {...}, history_count: n }
  422 { errors: [...] }                    # reason required, min 10 chars

GET  /api/v1/portfolios/:id/fitgap/:vacancy_id
  200 { status: "ready" | "pending" | "missing", report: {...} | null }

POST /api/v1/portfolios/:id/regenerate_fitgap
  202 { status: "pending" }                # never deletes the existing report

Frontend

The report page drives an explicit state machine instead of inferring state from HTTP 404s. The comparison table shows the AI rating beside the assessor rating, marks overridden rows, and exposes who overrode it, when, and why. Polling backs off and stops; it never re-triggers work.

6. Implementation

Changes landed as small, individually reviewable commits. The pull request checklist tracks progress; each item is checked only after its verification step passes.

7. Verification

Test matrix, seeded-fault evidence, and the AI verification moment are recorded here once the suite runs. The seeded fault removes tenant scoping on a scratch branch so the tenant spec fails, then reverts with history visible so it passes.

8. User experience

Loading, empty, pending, failed, and partial states; a dialog that refuses to submit an empty rationale; provenance that stays legible at narrow widths; and a report page that no longer implies certainty it does not have.

9. Trade-offs & next steps

What was deliberately not done in this slice, what it would cost, and what I would do first with more time — including signature verification on the tenant resolver, a dedicated history endpoint, and frontend unit tests.
